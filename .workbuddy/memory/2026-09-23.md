## 第一版真实存在的缺陷（重要，避免重犯）

1. **`IBKRBroker.account()` 从第一版起就是坏的**
   `__init__` 里 `self.account = account`（账户号字符串）**覆盖了同名的 `account()` 方法**，
   调用即 `TypeError: 'str' object is not callable`。
   → 已把属性重命名为 `account_id`。
   **教训：数据类属性与抽象方法同名是隐蔽陷阱，尤其当子类继承 ABC 时不会报错。**

2. **`IBKRBroker.quote()` 是假的** —— 它把请求转发给了 `data_provider.get_quote`（yfinance），
   完全没有用 IBKR 的 `reqMktData`。所谓"接入 IBKR"其实只接了账户，没接行情。
   → 已实现 `reqTickersAsync` 批量实时快照 + `reqHistoricalDataAsync` 历史 K 线。

3. **`positions()` 用成本价冒充现价** —— `px = avg`，且 `unrealized_pnl` 恒为 0.0。
   持仓浮盈永远是 0，等于没有盈亏信息。
   → 已改用 `ib.portfolio()` 取真实 marketPrice / marketValue / unrealizedPNL。

4. **ib_async 在自建事件循环里全部会抛 "This event loop is already running"**
   原因：同步方法（connect / qualifyContracts / reqTickers / reqHistoricalData /
   accountSummary / sleep）内部调用 `run_until_complete`，而我们的循环正在 `run_forever`。
   → 必须改用 Async 变体（`connectAsync` / `qualifyContractsAsync` / `reqTickersAsync` /
   `reqHistoricalDataAsync` / `accountSummaryAsync` / `asyncio.sleep`），
   通过 `run_coroutine_threadsafe` 投递。
   **而 `placeOrder` / `cancelOrder` / `reqMarketDataType` / `positions` / `portfolio` /
   `openTrades` / `fills` / `managedAccounts` 是纯发送或读缓存，可以直接调用。**

5. **实时引擎只能跑模拟盘**，实盘必须手动下单 —— 与"帮助我做量化交易"的核心诉求不符。
   → 已开放实盘模式（仍需三重锁），并加入**保护性委托**：建仓后在 IBKR 侧挂 GTC 止损单。

6. **回测前端只提供 1d/1wk/1h**，而日内策略族（ORB / VWAP / 日内动量）需要 5m/15m/30m。
   后端支持但前端没暴露 —— 等于日内策略不可用。
   → 已补齐，并新增「数据源」选择（IBKR 优先）。

7. **行情页用的是折线图**，不是 K 线 —— "行情分析"名不副实。
   → 已自绘 SVG 蜡烛图（实体+影线+成交量副图+均线叠加+十字光标+区间缩放）。

8. **导出功能的文件名含中文导致 UnicodeEncodeError**
   HTTP 头只能是 latin-1。
   → 改用 ASCII 回退名 + RFC 5987 `filename*=UTF-8''<percent-encoded>`。

9. **Vite 构建被主机的 safe-delete 保护拦截**
   `emptyOutDir: true` 会触发 fs.rmSync，被 genie-safe-delete 拦住，构建失败。
   → `emptyOutDir: false` + `scripts/prebuild.mjs` 用 **rename 归档**旧 dist（rename 不受拦截）。

# 第二轮：代码体检 + 核心功能补齐（P0/P1 修复 + 组合优化）

## 代码体检结论（两个子代理并行审查 + 逐文件确认）
后端 P0×1 / P1×5 / P2×3，前端 P1×2 / P2×7。全部修复。

## 已修复的缺陷（按严重度）

### P0
- **熔断对运行中引擎完全无效**：`EngineTask` 构造时冻结 `RiskLimits` 快照 →
  运行中启用熔断/收紧限额都被忽略。修：`live.py::_live_limits()` 每 tick 重读
  `appstate.get_risk_row()`；`run_once` 开头做熔断 + 实盘锁定热检查。

### P1
- **止损 ATR 是假的**：原用 `abs(p.last_price - px)`（现价与成本价之差）冒充 ATR。
  修：`_build_signals` 同批产出真实 ATR，新增 `_atr_for(sym)` 按需补算并缓存。
- **止损对引擎外持仓永不生效**：`_check_stops` 里 `if tr is None or not tr.s.active: continue`
  只创建 tracker 从不 `open()` → `s.active` 永远 False。修：新增 `STOP_TAKEOVER` 接管分支。
- **`broker` 字段对 IBKR 纸面账户写成 `simulated`** → `ibkr.py` 中
  `OrderRow.broker == "ibkr"` 的过滤失效，纸面订单状态永不回写。
  修：`_broker_name = getattr(broker, "name", "simulated")`。
- **伪造成交**：`filled_qty=res.filled_qty or qty`、`avg_fill_price=res.avg_price or ref_px`。
  IBKR 异步下单返回 `filled=0` 是常态 → 用户看到假成交价。
  修：两级取值（券商快照 > 下单返回），未成交不写价，`Fill` 仅在 `filled>0 and px>0` 时写入。
- **`Fill` / `PositionSnapshot` 两张表全项目零写入** → 新增 `_snapshot_positions(broker)`
  与成交落库。
- **前端实盘锁定永远失败**：`doUnlock(false)` 传空口令而后端强制校验。
  修：后端 `live_unlock` 仅对 `enable=True` 校验——**锁定是降险操作，不该比解锁更难**。

### P2
- **缓存不校验覆盖区间**（本轮新发现）：SPY 缓存仅 682 行（2024 起），
  请求 2019 起时直接命中短缓存 → 优化器把 SPY 判为「数据不足剔除」、回测静默跑错区间。
  修：`_read_cache` 增加 `start`/`end` 覆盖度校验（`_COVER_TOL`）；
  `_write_cache` 与旧缓存合并 + `_CACHE_MAX_ROWS` 截断。
- dry-run 复用运行中引擎会污染 `tick_count/last_tick` 且并发 → 改为一次性实例。
- `state.live_unlocked()` 返回内存标志与 DB 值矛盾 → 新增 `_ensure_live_loaded()` 首次访问时恢复。

## 新增核心功能：组合优化（`backend/app/engine/optimizer.py`，约 600 行）

**本机无 scipy / cvxpy，全部纯 numpy 自实现**：

| 环节 | 方法 |
|---|---|
| 收缩协方差 | Ledoit-Wolf 向对角阵收缩；用 `(X∘X)ᵀ(X∘X)/T` 恒等改写避免构造 T×N×N 张量 |
| 收缩期望 | Jorion Bayes-Stein：`w=(N+2)/((N+2)+T·(μ−μ₀1)ᵀΣ⁻¹(μ−μ₀1))` |
| 凸投影 | Dykstra 交替投影求 `{Σw=total, lo≤w≤hi} ∩ {Σ_{i∈C}w_i≤cap}` 的欧氏投影 |
| 目标求解 | Barzilai-Borwein 步长投影梯度上升（1500 次迭代 → <150 次；单目标 81s → 0.3s） |
| 有效前沿 | 按平均波动归一化后扫描 λ∈[1e-3,1e4]，只算一次并复用给切点组合定位 |
| 相关簇 | 并查集按 `|corr| ≥ threshold` 聚类 → 每簇总权重上限（伪分散防护） |

6 个目标：`max_sharpe` / `min_variance` / `max_return` / `risk_parity` / `inverse_vol` / `equal_weight`。

### 优化器自身的 4 个真 bug（均已修）
1. **期望收益恒为 0** —— `mu = estimate_mean(X, ...)` 传的却是去均值后的 `X`。
   修：协方差用去均值数据，期望收益必须用原始收益 `X_raw`。
2. **单次求解 81 秒** —— 固定步长 `1/L` + 1500 次迭代 + `project` 每步 40 轮 + 前沿重复计算。
   修：BB 步长 + `project` 加 `tol=1e-13` 提前退出 + 前沿只算一次。
3. **盒约束/簇约束被最终归一化破坏** —— `w = w/w.sum()*max_gross` 会把触顶权重推回上限之上。
   修：改为 `project(...)` 重新投影 + `is_feasible` 校验 + 不可行时退回等权兜底。
4. **静默放宽上限**（本轮验证时抓出）—— `max_weight × N < max_gross` 时自动放宽到 `1/N`，
   但 `constraints.max_weight` 仍写原值，用户以为 15% 被遵守、实际拿到 16.67%。
   修：新增 `constraints.effective_max_weight` + `max_weight_relaxed` 标志 + 显式备注
   + 前端黄色告警条。

## 关键教训（二轮）
- **漏 `@staticmethod` 的代价**：`@staticmethod` 被重写时丢掉 → 方法被当实例方法绑定 →
  `self._status_from_trade(trade)` 抛 `TypeError` 被 `except Exception` 吞掉 →
  **整条订单状态回报链路静默失效**。写宽泛的 `except` 时必须保证异常可见（现在会记入 `stats.events_dropped` 与 `last_error`）。
- **引用计数只能加一次**：`hub.ensure()` + `hub.subscribe_events()`（内部又 ensure）→ 计数为 2，
  退订只减 1 → 订阅永久泄漏。已给 `subscribe_events(ensure=…)` 加显式开关并把约定写进 docstring。
- **`locals().get("name")` 在循环里取变量是陷阱**：上一轮迭代的残留值会泄漏到本轮。
- **测试脚本的时序假设也要验证**：多处「失败」其实是断言写错了（快速失败被当成 bug、
  背压逐笔送达被当成合并失效、读取时机在 `stop()` 之后）。修断言前先确认实现语义是否正确。
- 该环境不要用 heredoc 写 Python（会被 shell 解析炸掉，表现为 SIGTERM 无输出）；用 Write 工具落盘再跑。

### ① 悬停无数值的真凶（关键教训）

教训：**"组件渲染了但数值全为破折号" = 索引/键类型不对，先怀疑小数索引**；`Number.isInteger` 已加进 hov 守卫。
