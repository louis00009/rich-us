## 双进度条 + Bridge 必读不同步（用户报告「监控 1/3 + 手动 1/4 同时显示 + AI Agent 数据没进必读/事件流」）
- **真根因①**：`app/intel/events.py::add_events` 只在 `if inserted:` 时触发 `refresh_async("events")` —— Bridge Agent 提交全 dedupe 命中（inserted=0）的场景**不刷必读**，前端 30s 轮询拿到的还是旧 digest。**修复**：`if inserted or touched:` —— 入库后只要本次有 commit/flush 即刷新兜底（桥的多 Agent 重复提交 → 确认 DB 最新状态 → 必读能立即看到）。
- **真根因②**：监控 SCHEDULER tick 与手动 ai-scrape 不互斥，**两条进度条同屏**让用户怀疑数据串了。
  - **后端 jobs 互斥锁** `app/intel/scrape.py::_SCRAPE_LOCK`（acquire/release/scrape_lock_state）：`ai_scrape_companies` 启动时 acquire、finally 释放；监控 tick 检测锁被占 → 整批跳过（输出 `error="locked: jobs 被 X 占用"`），不再写台账。
  - **前端 UI 隐藏**：MonitorBar 在 `scrapeJob` 存在时不渲染 LiveStatus（避免双进度条）；手动完成后监控下一 tick 自然恢复。
- **测试坑**：run_checks 那条「add_events inserted=0 也触发刷新」断言，用了固定 title "fresh news"，跑过两轮后 dedupe 命中 inserted=0 + touched 不增 → 修复后不满足触发条件。改成唯一 title（`_unique_title = f"refresh_async_test_{int(_t.time())}"`）+ 检查源码字符串 `if inserted or touched`（验证修复点真的落地），不再依赖 runtime 行为。
- **自检**：intel 148/148（新 6 条断言：jobs 锁 4 + refresh_async 2）。端到端实测 jobs 互斥：手动 acquired True → 监控 acquired False → 手动 release → 监控 acquired True。
- **用户反馈 → 落地原则**：用户报告「X + Y 都没工作」时，X 与 Y 往往是**两个独立 bug**，不要归并到一个修复里假装解决。
