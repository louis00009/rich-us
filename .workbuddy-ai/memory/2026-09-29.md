## 续 2：用户追问「AI 抓取为什么只抓 4 家」

### 根因
- 前端 `pages/Intel.tsx` 把家数**写死** `{ limit: 4 }`；后端 `ai_scrape_companies(limit=3)`
  默认 3、手动端点原上限 `min(12, …)`。
- 实际库况：**37 家 / 启用 33 家 / 待抓取 28 家** —— 所以「0/4 家」看起来像漏抓。
- 真相：这是**刻意的分批**。单家 = 1 次多源新闻聚合 + 最多 2 次 LLM 调用，推理型模型每次先烧
  上千 token 思维链；一次跑 28 家要十几分钟并会撞网关限流。监控运行时调度器每轮另抓 3 家轮转，
  长期会把全部标的覆盖一遍。
- **问题不在分批，在于没告诉用户**：`待抓取 N 家` 原本只藏在卡片底部 11px 灰字里，且没有任何地方
  解释「为什么只抓 4 家」。

### 改动
- 后端 `ai_scrape_companies`：`limit <= 0` 表示**全部**（原 `[:max(1, limit)]` 会把 0 夹成 1）。
- 后端 API：新增 `_norm_scrape_limit()`（`<=0` 原样通过 = 全部；正数夹到 `_SCRAPE_MAX=60`；
  非法输入回落 3），替换原来的 `min(12, …)`。
- 前端 `MonitorBar`：动作区加「本轮 [最多 4/8/12 家 | 全部 N 家 ▾]」下拉；进度条下方显式说明
  「本轮只抓 N 家，待抓取共 M 家 —— 刻意分批…再点一次继续下一批，或改成全部」；
  底部汇总行补「待抓取 N 家 / 共 M 家启用」+ 轮转机制说明。
- 默认仍是 4（不改变既有行为），把「全部」变成用户的**显式选择**。
- 守卫：后端 4 条（`_norm_scrape_limit` 语义 + overview 返回家数）+ 前端 4 条（下拉存在、
  含「全部」、写明分母、解释分批）。

### ⚠️ 顺带挖出一个**全站级**真实缺陷（比原问题严重）
`main.py` 的 SPA 回退是 `if (FRONTEND_DIST / "index.html").exists():` **条件注册**的。
我按流程「先起服务、再构建」时，构建已把 `dist/` 清空 → 回退路由**永不注册** →
`/intel`、`/rankings` 等**全部 404**，浏览器只显示 `{"detail":"Not Found"}`，
**重新构建也不恢复，必须重启后端**。
- 已改为**无条件注册** + **请求时**判断产物是否就绪：就绪返回 index.html，
  未就绪返回**可操作**的 503（「请执行 npm run build，无需重启后端」）。

  `loadBacktestPrefs()` 顺手把历史数组型偏好规范化成串。

## 事件：后台重启任务报 `failed`（**假警报**，服务其实好的）

收到通知：后台任务 `0OKQsl`（`run.py > runtime/service_restart.log`）**failed**，时长 14m16s。
第一反应是服务挂了 —— 而且**第一次查证"确实"显示端口没监听**，很容易就此下结论去重启。

**实际结论：服务是好的。** 最终状态 PID **24840**（`python3.11.exe`，215MB）稳定 LISTENING，
`/api/health` **200**，四个页面全 200，情报接口全部正常：

```
media=only     items=35   commentary=35   OK 全部为媒体评论
media=exclude  items=200  commentary=0    OK 无媒体评论
digest         top=12     commentary=0    tiers=['critical']  engine=local
overview       pending=25 enabled=33
```

### 为什么会出现两个假信号（都值得记）

1. **「查端口说没监听」是重启窗口的竞态。** 旧进程（24828）已死、新进程（24840）还没 bind，
   这一瞬间 netstat 里 8787 只剩 `FIN_WAIT_2 24828` 的残连接，**grep LISTEN 自然为空**。
   几十秒后同一命令就正常了。→ **等 10~15 秒复查，别立刻动手重启。**
2. **「任务报 failed」是因为它的子进程被顶掉了。** 17:43:22 有一次**更新的重启**（新进程 24840），
   旧进程 24828 随之退出 → 启动它的那个后台任务看到子进程结束 → 记 failed。
   **任务失败 ≠ 服务失败**，重启类任务被后续重启取代时必然报 failed。

### 顺带一个日志陷阱

`> runtime/service_restart.log` 是**截断**写入。两个进程先后写同一路径，会得到
「**开头是新进程的启动 banner，结尾是旧进程十几分钟前的日志**」这种**时间倒流**的混合内容
（我第一次 `head` 看到 17:43:22 启动、`tail` 看到 17:43:05 的 yfinance 报错，文件大小还在两次读取间
从 498KB 掉到 1894B）。**不要据这种日志判断"崩溃/时序"**；判断进程存活要用
`tasklist //FI "PID eq N" //FO CSV`。

### 日志里的报错都是正常噪音（不是崩溃）

`yfinance ... possibly delisted`（44 个，源于同文件上方 `Crumb fetch rate-limited HTTP 429`）、
`ib_async ... ConnectionRefusedError 127.0.0.1:7497`（TWS 没开）—— 全部无 traceback，
最后一行是 `首页预热完成`，属正常启动完成。

> `run.py` 是 `reload=False`，没有 reloader 子进程：`Started server process [PID]` 里的 PID
> **就是服务进程本身**（24840 已核实存活），所以不需要再找 parent。

### ⚠️ 拆分时最容易踩的一个坑：`runKey` 与 payload 的格式**不一样**
原页面的 `AIAssist` 里：
- payload 的 `sort` 是 `` `${sort} ${dir}` ``（**空格**分隔）
- `runKey` 是 `` `${sort}:${dir}:${rows.length}:…` ``（**冒号**分隔）

若把两者合并成一个 `sortKey` 字符串传进子组件，`runKey` 会**悄悄变成空格版** ——
后果是「只改排序方向时 runKey 不变 → AI 结果不重置」，属于**静默行为回归**，构建/typecheck 全拦不住。
正确做法：`PoolAiReview` 接收**分开的** `sort` / `dir`，在组件内各自拼各自的格式。
