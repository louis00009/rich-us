### ⚠️ 本轮挖出一个既有严重缺陷（值得记住）
**`alerts.py` 的技术类提示通道一直是死的。**
`from datetime import datetime as _dt` 使 `_dt` 是**类**而非模块，
`_dt.timedelta` 恒抛 `AttributeError`；而该行原本写在 `try/except: pass` 里 →
异常被吞 → **`_tech_alerts()` 从未执行过**，52周高低/放量/跳空/RSI/摆动
全部失效（只有日内急涨跌 + 新闻两类在工作）。
本次并行化时把该行移出 try，缺陷立刻暴露。修复：`timedelta as _td`。
验证：修复后 `scan(force=True)` → scanned=12 / candidates=16 / created=6 / 18.8s
（此前是「跑 102s 但技术类候选恒为 0」）。

**这是「静默吞异常掩盖代码缺陷」的实证案例**，也印证了 B 类里 `_silent()` 的价值。
排查手法：**把可疑的 `try/except: pass` 临时去掉，看是否立刻抛异常** ——
比读代码快得多。

用 AskUserQuestion 问了三件事，用户选择：

### ⚠️ 诚实性立场：不能说「可买入」
本项目自己的复盘结论（本轮再次引用）：**规则化策略在收益上打不过买入持有**
（同期 SPY +245%、QQQ +404%），真实价值在回撤控制。所以按规则挑股票会涨的说法
在本项目内没有证据。落地时**全链路都标注「不是买入信号」**：

### 实测数据（本机 2026-09-27）
- **1 年日线全量 503 只 = 60.9s**（4 线程 50 只/块）；换 2 年窗口后 **71.2s**。
- 只落**算好的指标**（非原始 K 线）= **95 KB / 503 只**（原始日线约 1 MB+）。
- 覆盖率：503/503 只拿到、MA200 可用 501、Beta 可用 503。
- 评分分布（501 只）：**≥70 共 52 只**、50~70 共 215、<50 共 232、na 2。

### 技术指标模块（`backend/app/technicals.py`，396 行）
三层缓存与 `fundamentals.py` 完全一致（内存 TTL + 磁盘快照 + 单飞 + **覆盖率闸门**）。
- TTL **3600s**（不是 600s）：日线是**日频**数据，盘中重拉不会产生新 K 线，纯浪费。
  行情刷新会顺带触发它，但受这个 TTL 闸门约束，新鲜就直接返回。
- `MIN_BARS = 210`：不够就返回 None，**不硬算**（用 3 根 K 线算「200 日均线」是错的，页面看不出）。

### 🔴 本轮踩的两个「静默失效」坑（都不报错，只是数据全是 None）
1. **Beta 全部为 0 只可用** —— yfinance 即便只下 **1 个标的**也返回 MultiIndex
   （列是 `('Close','SPY')`），此时 `df["Close"]` 直接抛 KeyError，
   被我函数里的 `except Exception` 吞掉。**压平 MultiIndex 必须在取列之前。**
   修完 Beta 立刻正常：AAPL 1.07 / NVDA 1.86 / BRK-B 0.39 / KO -0.02（与真实值吻合）。
   顺带把「基准拉取失败」记进 `_state["bench_error"]` 暴露给前端 —— 否则基准挂了
   只表现为「Beta 一列全是 —」，完全看不出是基准的问题。
2. **`r1y` / `excess_1y` 永远为 None** —— `period="1y"` 只返回 **251** 根 K 线，
   而「近 1 年收益」需要 **252** 根（今日 + 251 根之前那天）。差一根 → 静默全空，
   连带「相对 SPY 超额」筛选变成永远选不出东西的空功能。
   **改用 `period="2y"`**（≈502 根），请求数不变只是 payload 大一点。
   回归用例：断言 `_FETCH_PERIOD != "1y"` 并写清原因。

### 评分设计（`backend/app/scoring.py`，275 行）
四维：估值 30% / 质量 30% / 位置 20% / 趋势 20%，各自 0~100 再加权。
- **估值以「同行业 PE 分位」为主**（不是绝对 PE）：否则整个金融板块会被捧成「最便宜」。
- **ROE 在 30% 封顶**：实测 ROE 中位数 17%，但 LVS 288%、MA 284%、AAPL 118% ——
  这些**不是数据错误**，是大额回购让净资产趋近 0（Apple 典型）。当「极优质」会系统性
  高估一批靠回购撑 ROE 的公司。封顶并在理由里标注「可能由回购推高」。
- **波动率惩罚**：年化 > 60% 每超 10% 扣 6 分。
- **缺失值语义（最重要）**：缺数据的维度**不计入总分、权重重归一**，并标 `low_confidence`。
  反面做法（当 0 分）会让腾讯不覆盖的 50 多只小票被系统性判成「差」且无任何提示。
- 🔴 **`MIN_DIMS` 差点造成「功能坏了」的假象**：原写法 `available < MIN_DIMS` 无条件生效，
  用户**故意只勾一个维度**时（完全合理的用法），所有股票总分都变 None。
  改为 `enabled >= MIN_DIMS and available < MIN_DIMS` 才拦：
  · 用户故意只启用 1 维 → 尊重，用这 1 维算分；
  · 启用 4 维却只有 1 维有数据 → 数据不足，不给分。
  这个 bug 是**在真实浏览器里点「只按趋势打分」才暴露的**（单测当时只覆盖了 2 维和 0 维）。

## 第十一轮补 · 榜单页「TMO 搜不出来」根因（用户报障）

### 症状 vs 真相
用户报「`/rankings` 数据还是不全，TMO 居然都搜不出来」。
**数据其实是全的**：`sp500_quotes.json` 503 只、`sp500.json` 成分股 503 只，
两边**完全一致（差集为空）**；TMO 在基本面缓存里字段齐全
（PE 36.33 / EPS 18.58 / PB 4.74 / 股息率 0.27% / 市值 2496 亿）。
覆盖率：基本面 501/503、技术指标 499/503。**没有数据缺失问题。**

### 真根因：搜索 `q` 与候选池评分门槛 `score_min` 被 AND 在一起
`rankings()` 里 `q` 在**开头**过滤行、`score_min` 在**结尾**过滤行，两者是 AND。
用户在「候选观察池」视图（前端自动带 `score_min = threshold = 70`）搜 `TMO`：
**TMO 综合分 40.2 < 70 → 被门槛挡掉 → 接口返回 0 行**，
页面显示「没有匹配的标的 —— 放宽筛选条件、降低评分阈值或调整搜索关键词后重试」。
用户看到的就是「这只股票不存在」。

**语义错误**：`score_min` 是候选池视图**自动加的隐含门槛**，不是用户主动勾的筛选条件；
而用户输入一个明确代码是在**查这只股票**，不是浏览候选池 —— 必须能查到。

### 修复（4 处）
1. `rankings.py`：`effective_score_min = None if q_lower else score_min`
   —— **搜索时忽略评分门槛**。⚠️ 用户主动设置的 PE/RSI/均线等筛选**不受影响**，仍生效。
2. `rankings.py`：新增 `_match_rank()`，代码由**子串**匹配收紧为**精确/前缀**匹配。
   旧 `ql in sym.lower()` 让 `TMO` 命中 `ATMOS Energy`（a-**tmo**-s）——
   搜一个明确代码却混进无关公司，正主还被按涨跌幅排到后面。
   名称匹配 `_name_match()`：拉丁文按**词首**（`fisher`→Thermo Fisher），
   CJK 按**子串**（`赛默飞`→赛默飞世尔）—— 用 `_CJK_RE` 判定走哪条路。
3. `rankings.py`：命中质量作**主排序键**（精确 0 > 前缀 1 > 名称 2），
   用稳定排序实现（先按用户选择的列排，再按 `_match_rank` 排）；`_match_rank` 返回前 `pop` 掉。
4. 顺带修：**中文名搜索以前完全不可用** —— `enrich()`（注入 `name_cn`）原先在 `q` 过滤**之后**，
   所以「赛默飞」永远搜不到。已把 enrich 提前到匹配之前（503 只一次 DB 查询，开销可忽略）。

前端：`RankResp` 加 `pool_bypassed`；`PoolNotice` 加 `bypassed` 提示
（「正在搜索，已临时忽略评分门槛（≥ 70）…」）；空态文案按 `q` 分支；
搜索框 placeholder 改「搜索代码 / 中英文名称」。

## 第十六轮 · TwelveData 多 Key 轮询池 + 数据源链修正

### 两个源的实测结论
- **finnhub：接上了，但免费档没有 K 线权限**。`quote`/`news` 可用，`/stock/candle`
  返回 `{"error":"You don't have access to this resource."}` → 只能当**报价/新闻**源，
  **不能**当历史数据源（链上它仍在最后一位兜底，但拿不到 K 线）。
- **twelvedata：Key 有效**。免费档实测（`/api_usage`）**8 credits/分钟、800 credits/天**。
  单账号喂不饱全量标的 → 这正是要多 Key 轮询的原因。

### 后端交付
- **新增 `app/twelvedata.py`（486 行）**：多 Key 轮询池
  - 密钥 **Fernet 加密落库**（`AppSetting.twelvedata_keys`），与 AI key/券商口令同一套机制；
    API 只回**掩码**（前 4 + 后 4，如 `81d0****c6c1`），明文不进日志/响应。
  - `KeyPool`：`_cursor` 轮询；**每 Key 各自**维护「60s 滑动窗口」+「当日计数」；
    冷却 429 → 62s、401/403 → 900s；`_MAX_KEYS=50` 防误粘贴撑爆。
  - **限流器即安全阀**：额度耗尽 `acquire()` 返回 `None` → 降级链自然落到下一个源，
    **不阻塞、不 429 雪崩**。
  - ⚠️ **限流可能返回 HTTP 200 + body `{"code":429}`**（不只是 HTTP 429）→
    必须**同时判 body**，只判状态码会漏。
  - `.env` 的 `TWELVEDATA_API_KEY` **只用于首次播种**（之后以界面增删为准）。
- **数据源接入**：`_from_twelvedata` + `v_td` + `TwelveDataProvider`（`register_twelvedata_provider`）。
  链位：`yfinance → stooq → twelvedata → finnhub`（刻意放 stooq 之后，限流器兜底）。
- **新增 6 个端点**（`api/market.py`）：`GET /market/twelvedata`、
  `POST /market/twelvedata/keys`、`PATCH/DELETE /market/twelvedata/keys/{kid}`、

### 三个静默错坑（都是「不报错但数据错」，已逐个钉住）
1. **时区**：TwelveData 的 `datetime` 是**无时区的交易所墙钟**。直接交给 `_normalize`
   （默认把 naive 当 UTC 再转 NY）→ 日线整体退到**前一天 20:00**，回测系统性错位一天。
   → 修法：`_from_twelvedata` 先 `tz_localize("America/New_York")` 变 **aware**，
   由 `fetch_history` 做**唯一一次**归一化。
2. **`_normalize` 不是幂等**：aware→naive 只应发生**一次**；重复跑会把这个 naive 当 UTC
   再退 4 小时。`v_td`（降级链）与 provider 路径**互斥**，所以恰好一次。
   （我原先在测试里写「对 aware 输入幂等」是**错的**，被自己的测试抓出来后改成
   「恰好一次 + 两个陷阱固化」。）
3. **`outputsize=5000` 分支不认 `end`**：日线/周线会返回「2006 年至今全量」，
   指定 `end` 的回测会读到 end 之后的 K 线 = **未来函数**。
   → 新增 `twelvedata.clip_range()`（**纯函数、可自检**）本地裁剪；
     日线/周线含 end 当日，日内取到 end 当日收盘。
